## 3. State อยู่ที่ไหน ทำไม

### (ก) ทำไมคำค้นและธาตุอยู่ใน URL ไม่ใช่ `useState`

คำค้น (`?q=`) และธาตุ (`?type=`) อ่าน/เขียนผ่าน `useSearchParams` อย่างเดียว ไม่เก็บซ้ำใน `useState`
สิ่งที่ผู้ใช้ได้คือ: copy URL อย่าง `/pokemon?q=saur&type=grass` ส่งเพื่อนแล้วเปิดได้ผลลัพธ์เดียวกันทันที
(เปิดแท็บใหม่ก็ตรง), กด back/forward ของเบราว์เซอร์แล้วย้อนสถานะการค้นหาได้, refresh แล้วค่าค้นหาไม่หาย
และพิมพ์คำค้นหลายตัวอักษรไม่สร้าง history ทีละตัว (ใช้ `replace: true`) กด back ครั้งเดียวจึงออกจากการค้นหา 

### (ข) ทำไมทีมหยุดที่ Context

ไล่ตาม decision framework: `useState` ในหน้าเดียวไม่พอเพราะทีมต้องใช้พร้อมกันหลายที่
(Nav แสดง `ทีม (n/6)`, หน้า `/pokemon`, หน้ารายละเอียด, หน้า `/team`) — ถ้า lift state ขึ้น App
ต้อง prop-drilling ผ่าน route หลายชั้นและทุกหน้าต้องรับ props ที่ไม่เกี่ยวกับตัวเอง
Context จึงพอดี: state มีโดเมนเดียว (ทีม 0–6 ตัว), อัปเดตไม่ถี่, ไม่มี async/middleware ซับซ้อน
และ persist ลง `localStorage` ได้ใน `TeamProvider` ที่เดียว ส่วน Redux/Zustand เกินความจำเป็น
(โจทย์ห้ามใช้ด้วย) เพราะไม่มี global state หลายโดเมนหรือ logic ข้าม slice ให้จัดการ

### (ค) `memo` / `useMemo` / `useCallback` — หรือเหตุผลที่ไม่ใช้

ใช้ `useMemo` 3 จุด: แปลงรายชื่อธาตุเป็น `Set` ของ id, กรองรายชื่อ 151 ตัวตามคำค้น+ธาตุ,
และสร้าง zod schema ที่ผูกกับชื่อสมาชิกทีมปัจจุบัน — ทั้งหมดเป็น derived data ที่คำนวณใหม่
เฉพาะเมื่อ input เปลี่ยน ไม่ได้เก็บเป็น state แยก ไม่ได้ใช้ `memo`/`useCallback`
เพราะแอปเล็ก (การ์ดสูงสุด 151 ใบ ไม่มี render หนัก) ไม่มี prop callback ส่งลึกหลายชั้น
จึงยังไม่คุ้มและไม่แก้ปัญหาอะไรที่วัดได้
